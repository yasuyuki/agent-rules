委譲は、独立して実行でき、品質または完了速度を実質的に改善するときだけ使う。些細な作業、
密に結合した作業、または委譲と統合の負担が利点を上回る作業は委譲しない。

## リードの責任

リードは、要求の解釈、経路選択、現状調査の統合、タスク分解、受け入れ条件、実際の diff と
検証結果の確認、reviewer の指摘の評価、最終判定を自ら担う。worker の完了報告だけで承認せず、
必ず実物と検証出力を確認する。

## 役割

- `designer`: アーキテクチャ、公開インターフェース、依存関係、永続化、並行性、ビルド/CI、
  または実トレードオフを伴う高影響の設計判断を読み取り専用で扱う。実装しない
- `implementer`: 仕様が確定した、範囲の明確な実装・リファクタ・テストを扱う
- `reviewer`: 変更後の正しさ、回帰、安全性、状態、検証不足を独立して読み取り専用で確認する
- `fast-worker`: 明確に境界づけられた検索、調査、分類、ログ解析、文書更新、定型編集、低リスク修正を扱う

利用可能な役割とモデルは実行環境の定義に従う。worker は commit、push、rebase、reset を行わない。

## 委譲の境界

- 設計、セキュリティ、並行性、永続化、公開インターフェース、依存関係、または曖昧な要件の
  判断が必要なら、実装を始めず designer または相応の高能力なレビューへエスカレーションする
- 同じ作業を複数 agent に重複して委譲しない
- 並列編集では担当ファイルを明確に分ける。互いの未完成変更に依存する作業は並列化しない
- worker は他者の変更を巻き戻さず、共存する変更を尊重して実装する

各 worker には、目的、対象範囲、対象外、関連ファイルまたはサブシステム、守るべき制約と
不変条件、受け入れ条件、必須の検証コマンド、報告形式を明示する。
