---
id: msw-necessity
title: MSW 必要性規則
summary: 要求の最小受け入れ条件を先に定め、必要または未証明な主張だけを最小の行動と証拠で閉じる。
---

作業開始時に contract、すなわち要求された deliverable と最小受け入れ条件、保存先と
branch ごとの必要差分を定義する。既存の記述・入口で満たせる事項を先に除く。計画、変更、
テスト、レビュー指摘、追加調査の各 claim `c` は、`c` を削除すると contract が未達または未証明になる
ときだけ採用する。

contract は利用者が必要とする機能と明示された制約から定める。既存script、起動手順、引数、
出力、test、過去の計画の維持を目的に置き換えない。対象の責務・改善方針を定める文書がある場合は
変更前に読み、適用範囲を確認する。実験装置の `CONSTITUTION.md` と `docs/IMPROVEMENT-POLICY.md`
は同位であり、装置を変更するときは両方を読む。装置固有の目的を他の製品の目的にはしない。

既存要素も追加案も、削除 → 責務外への分離 → 簡素化 → 維持 → 追加の順に検討する。
維持・追加の根拠は、それがないと失われる具体的な利用者機能または必要な不変条件とする。
自作wrapperを前提にして「wrapperがないと既存手順が動かない」と説明するのは循環である。
呼出先を含めて既存の公開入口で実現できるか確認し、移設・改名・生成script化だけで削減としない。

重大な失敗への必要な対策は既存の通常入口・データ構造・platform 機能へ実装する。
補助 command や test があるだけ、任意の注意書きだけでは実行経路の対策としない。
コードで実現できない判断だけ skill、残る上位方針だけ規約へ置く。手間はコード化不能の理由にしない。
不要な対策をコードへ移して温存しない。

容易に回復できる問題、対象の利用経路で発生前提が成立しない問題には、対策・恒久文書・
未解決台帳・Issue を追加しない。人間の監視・承認待ち・反復操作も回復負担に含める。
未観測を到達不能とせず、既存防御がある場合はそれを除いた影響で判断する。
明示要求、必要なデータ保護、既存の承認境界はこの除外で取り消さない。

情報の編集正本は一つにする。agent 向け恒久文書にはコード・help から取得できない目的・判断・
外部契約だけを残し、動作・引数・既定値・入力制約はコードを正本とする。必要なら help や近接コメントを
改善する。別文書への移設だけで削減としない。実行契約の目的・許可・受入条件は削らない。
他の文書は取得可能な正本への短い索引とし、生成配布物は機械的に一致するコピーにする。
人間用マニュアルの目的別説明は残してよいが、引数一覧などを別の手書き正本にしない。
対象・条件・成功判定を保ち、README は目的・最短の利用開始・マニュアルへの入口に絞る。

文書の作成・変更前に、人間向けは `optimize-human-docs`、agent 向けは `optimize-agent-docs`
skill を使う。読者が混在する文書では、それぞれ該当部分だけに適用する。

公開ツールは private な実行コードや本人環境の固定値を必須依存にせず、環境差は明示設定で渡す。
公開 skill は小さく独立利用可能にし、特定 repo・私的設定・モデル・MCP・専用 CLI を実行時の
必須依存にしない。起動・設定・依存関係の変更は公開コードと別配置の合成設定だけで受け入れを検証する。
本人環境や wrapper 専用 test の成功だけで独立性を証明しない。

採用した claim は、必要性に見合う最小で信頼できる行動と証拠で閉じる。有用、包括的、または可能で
あるだけでは採用理由にならない。contract が満たされ証明された時点で停止する。

検索・分類・Issue 登録は既存の会話と `gh`、`rg` などで完了させる。補助コードは、それなしでは
未証明になる事項を先に示し、その抽出だけに限定する。正確な時間集計が不要な依頼に全ログ集計や
新しい CLI・wrapper を持ち込まない。内容の読取は必要箇所へ絞り、既知の実行経路を使う。

保存は既存の適切な文書への必要差分に絞る。再開状態は handoff、長期計画は phased-plan-execution
に従い、完了後に捨てる長文を反復改稿しない。複数配置が必要なら確定した内容を再利用する。
検証・commit・共通 preflight は各規則どおり行い、工程削減と成果物の品質を実作業で確認する。
文書改訂や単発の成功だけで、継続的な改善や時間短縮を証明したとは扱わない。

上位の指示、明示的なユーザー要求、安全要件、既存の承認境界を優先する。上位根拠、明示的要求、
技術または platform contract、project policy、または必要性を示す測定なしに、数値上限、件数、
閾値、予算を設定しない。
